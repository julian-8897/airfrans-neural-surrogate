# Check the Transolver forward implementation

After protocol approval, run the check in the registered qualification job on a full A100. Use the [complete training stage and its normaliser](original-data-staging.md). The job environment needs CUDA-enabled PyTorch, PyVista, `timm` and `einops`. Preserve the environment with the run record.

```bash
python -m airfoil_surrogate.models.transolver_parity \
  /path/to/pinned/Transolver.py /path/to/train /path/to/normaliser.json \
  --case airFoil2D_SST_31.283_-4.156_0.919_6.98_14.32 \
  --out "$EXP_OUT/transolver-parity.json"
```

Pass the authors' `Airfoil-Design-AirfRANS/models/Transolver.py` at revision `75e0f67643806a81cd1d3f6adc88dd8c02416fe7`. The command verifies the source SHA-256 before execution. It initialises the reference at seed 0 and copies its forward parameters to the local model. The JSON lists the mapped and unused weights and the grid generated by the local model. [Pinned Transolver source](https://github.com/thuml/Transolver/blob/75e0f67643806a81cd1d3f6adc88dd8c02416fe7/Airfoil-Design-AirfRANS/models/Transolver.py).

The two models receive the same positional and normalised input tensors. The check uses two disjoint 4,096-node subsets and the full original mesh, with FP32 matmul at its highest precision. The JSON records maximum absolute and RMS differences in each channel. When a forward check exceeds the proposed tolerances, the command writes the discrepancies and exits with status 1.

## Time the production training path

Use `configs/original-a100-qualification.sbatch` for the registered 30-minute qualification allocation. The job runs parity first, then the timing command on the same A100. Give it the pinned source, complete train and validation stages, training normaliser, passing force-audit JSON and parity case ID. Use a prepared environment with the repository dependencies, `timm` and `einops`.

The timing command reads and packs the 12 audited training cases and all 80 validation cases from the original stages. It runs 11 short epochs with the production sampler, model, precision, optimiser and checkpoint writer, using a OneCycle schedule sized for the short timing trial. This trial produces no eligible checkpoint for the full study. The estimator drops the first epoch from training-update timing, scales the slowest timed training-only epoch to 720 cases and 398 epochs, and scales the slower validation increment to the 40 scheduled rounds. It also estimates full data loading and includes time outside the timed epochs, including checkpoint writes. The resulting cost and CUDA memory peaks are recorded in `training-preflight/preflight.json`, alongside the raw timings in `training-preflight/timing-attempt/metrics.jsonl`.

The timing command exits unsuccessfully if the projected training allocation exceeds the 23 A100-hour reservation. Check that projection against the actual Slurm allocation accounting, including elapsed qualification and remaining inference and recovery reservations, before submitting full training. The timing subset estimates throughput and loading from a small sample. It provides measured diagnostics for this hardware and staging setup, while actual full-run consumption is charged from Slurm.
